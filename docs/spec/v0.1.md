# SynodSQL specification v0.1

Status: **draft**, Phase 0. Oct 12, 2026.

This document fixes the data formats that every node must agree on byte for byte. It is taken from the white paper ([`docs/whitepaper.pdf`](../whitepaper.pdf)). Where this document and the white paper differ, this document is correct, and Section 9 lists each difference.

Sections 2 to 4 are **normative and implemented** in `crates/synod-core`. Sections 5 to 8 are **normative drafts**: later phases implement them, and they can change until that phase ends.

The words MUST, MUST NOT, and SHOULD have their RFC 2119 meanings.

## 1. Conventions

- All integers are big-endian, with fixed widths. No format uses variable-length integers.
- `u8`, `u16`, `u32`, `u64`, `u128` are unsigned; `i64`, `i128` are two's complement.
- `bytes32` is 32 bytes.
- `len32(x)` is a `u32` byte or item count, then `x`.
- `||` joins byte strings.
- All hashes are BLAKE3 with 32-byte output. Each hash kind uses BLAKE3 key-derivation mode with its own context string, so that a hash of one kind can never equal a hash of another kind.

| Hash kind | Context string |
| --- | --- |
| Row hash | `SynodSQL 2026-10-12 row hash v1` |
| Log hash | `SynodSQL 2026-10-12 log hash v1` |
| Manifest hash | `SynodSQL 2026-10-12 manifest hash v1` |
| Conflict ID | `SynodSQL 2026-10-12 conflict id v1` |
| Prolly tree node | `SynodSQL 2026-10-12 tree node v1` |

## 2. Identifiers

### 2.1 Node ID

A node ID is a `u32`. Each member node has a unique node ID. A node ID is never given to a second node, also after the first node leaves.

### 2.2 Row ID

A row ID is a `u128`:

```
bits 127..96   origin node ID (u32)
bits  95..32   local counter (u64)
bits  31..0    reserved, MUST be 0 in v0.1
```

The encoding is 16 bytes, big-endian. Byte order is ID order, which is (node, counter). A decoder MUST reject an ID with reserved bits that are not 0.

**Allocation.** A node gives out counters in increasing order. Before it gives out a counter `c`, a durable high-water mark `h > c` MUST be on disk. After a restart, the node continues at the persisted `h`. Counters can be skipped. They MUST NOT be reused. An implementation SHOULD reserve counters in blocks, so that it writes the mark once per block.

### 2.3 Transaction ID

A transaction ID is (node ID `u32`, counter `u64`), 12 bytes. The node gives out transaction counters by the same rule as row counters (Section 2.2), from a separate counter.

## 3. Hybrid logical clock

### 3.1 Layout

An HLC value is a `u64`:

```
bits 63..16   physical time, milliseconds since the Unix epoch (48 bits)
bits 15..0    logical counter (16 bits)
```

The numeric order of the `u64` is the HLC order. The encoding is 8 bytes, big-endian.

### 3.2 Rules

Let `pt` be the local physical clock, and `last` the last value that the node gave out.

- **Local event or send:** if `pt > physical(last)`, the new value is `(pt, 0)`. Otherwise it is `last + 1`.
- **Receive of remote value `r`:** first apply the drift check. Then let `m = max(last, r)`. If `pt > physical(m)`, the new value is `(pt, 0)`. Otherwise it is `m + 1`.
- **Overflow:** `+ 1` is on the `u64`, so a logical counter of `0xFFFF` carries into the physical part. The clock then runs at most 1 ms ahead for each 65,536 events in one millisecond.

These rules give the same values as the algorithm of Kulkarni et al., except at the carry.

### 3.3 Drift check

Each node has a drift limit `D` in milliseconds. A node MUST reject a remote value `r` with `physical(r) > pt + D`, and its clock MUST NOT change. The node SHOULD raise an alert. The default `D` is 500 ms.

### 3.4 Restart

The clock MUST NOT go backward across a restart. Before a node gives out a value with physical part above a persisted bound `b`, it MUST persist a new bound. After a restart, it resumes from `(b, 0)`. (Phase 1. The Phase 0 library takes the start value from the caller.)

### 3.5 Stamp

A stamp is (HLC, node ID). Stamps are ordered by HLC, then node ID. This is the total order of last-writer-wins. The encoding is 12 bytes: HLC (8) `||` node ID (4), so byte order is stamp order.

## 4. Canonical encoding

Every value and every row has exactly one encoding. A decoder MUST reject any other byte string, so that for each value there is one byte string, and for each byte string at most one value.

### 4.1 Values

Each value is a one-byte tag and a payload.

| Tag | Type | Payload | Canonical form |
| --- | --- | --- | --- |
| `0x00` | NULL | none | |
| `0x01` | INTEGER | `i64` | |
| `0x02` | REAL | `u64`: the IEEE 754 binary64 bits | Every NaN is `0x7FF8000000000000`. `-0.0` and `+0.0` are different values. |
| `0x03` | DECIMAL | scale `u8`, units `i128`; value = units × 10^(−scale) | scale ≤ 38. If units ≠ 0 and scale > 0, then units mod 10 ≠ 0. If units = 0, then scale = 0. |
| `0x04` | TEXT | `len32(UTF-8 bytes)` | Valid UTF-8. No Unicode normalization: the bytes are the value. |
| `0x05` | BLOB | `len32(bytes)` | |
| `0x06` | SET | `len32(items)`, each item a value | Items sorted by their encoded bytes, strictly ascending (no duplicates). An item MUST NOT be a SET. |

Tags `0x07` to `0xFF` are reserved.

**Equality and order.** Two values are equal if and only if their encodings are equal. Where the merge needs an order of values (for example `max` or `min`), it is the byte-wise order of the encodings. This order is not SQL order. A column type MAY define its own order for `max` and `min` in a later version.

**Why NaN is canonical.** The NaN that an operation makes has different bits on x86-64 and on ARM64. Without one NaN, two nodes could store different bytes for "the same" value.

**Why decimals are normalized.** `0.10` and `0.1` are the same number. A `DECIMAL(10,2)` column shows two digits, but the stored value is normalized.

### 4.2 Managed tables and types

Every managed table MUST be a SQLite `STRICT` table, so that a value has one type on every node. The mapping is:

| SQL type | Value type |
| --- | --- |
| `INTEGER` | INTEGER |
| `REAL` | REAL |
| `DECIMAL(p,s)` | DECIMAL; stored as normalized TEXT or BLOB in SQLite |
| `TEXT` | TEXT |
| `BLOB` | BLOB |
| `SET<T>` | SET; stored as BLOB in SQLite |

### 4.3 Rows

A row in its replicated form is the row ID, a tombstone flag, and one cell per column in schema order. Each cell is the stamp of the last write to the column and its value.

```
row      = version:u8 (= 0x01)
           || row_id:16
           || flags:u8          bit 0 = tombstone; bits 1..7 MUST be 0
           || count:u16         number of columns
           || cell × count
cell     = stamp:12 || value
```

Column names are not in the row. The schema gives the order. A schema change (Section 7.7 of the white paper) is a new schema epoch, and it re-encodes every row.

The stamps are part of the row, so they are part of the shared state and of the root hash. This is necessary: a later last-writer-wins merge reads the stamps, so two nodes with equal values but different stamps would diverge later.

A tombstone keeps its last column values. The `flag` delete rule and the revert tool use them.

### 4.4 Row hash

```
row_hash = BLAKE3-derive-key("SynodSQL 2026-10-12 row hash v1", row)
```

`crates/synod-core/tests/vectors.rs` holds pinned test vectors. CI runs them on x86-64 and ARM64.

## 5. Epoch log (draft, Phase 1)

A node writes one log per epoch, `B(e, i)`. The log is append-only while the epoch is open.

```
log      = header || entry* || footer
header   = magic "SYNODLOG" || version:u8 (= 0x01)
           || node:u32 || epoch:u64
           || base_root:bytes32         root hash of M(e-1)
           || schema_epoch:u64
entry    = len:u32 || body || crc32c(body):u32
body     = op:u8                        0x01 insert, 0x02 update, 0x03 delete
           || table:u32                 table ID from the schema
           || row_id:16
           || txn:12
           || hlc:8
           || before:image              absent (count 0xFFFF) for insert
           || after:image               absent (count 0xFFFF) for delete
image    = count:u16 || value × count   all columns, in schema order
footer   = 0xFFFFFFFF:u32 || entries:u64 || sealed_at:hlc
```

- The CRC on each entry finds a torn tail after a crash. Recovery cuts the log at the first entry with a bad length or CRC. An entry is committed only after its transaction is durable, so this loses no committed write.
- The stamp of each changed column is (entry HLC, header node).
- **Seal.** At the epoch boundary, the node writes the footer and syncs. The log hash is `BLAKE3-derive-key(log hash context, all bytes of the log)`.
- In a log, the entries of one row are in HLC order. The merge keeps the first before-image and the last after-image of each node (white paper, Section 6.1).

## 6. Manifest (draft, Phase 3)

```
manifest = magic "SYNODMAN" || version:u8 (= 0x01)
           || epoch:u64 || leader:u32 || schema_epoch:u64
           || base_root:bytes32
           || count:u32 || log_ref × count
log_ref  = node:u32 || log_epoch:u64 || log_hash:bytes32
```

- `log_ref` items are sorted by (node, log_epoch) and unique. A late log has `log_epoch < epoch`.
- The manifest hash is `BLAKE3-derive-key(manifest hash context, manifest)`.
- **Leader priority.** For epoch `e` with members sorted by node ID `n[0..N]`, the leader of rank `k` is `n[(e + k) mod N]`. Rank 0 has the highest priority. A node accepts the manifest of the highest-priority leader that it can reach. If it later sees a higher-priority manifest for the same epoch, it discards its `M(e)` and merges again.

## 7. Merge rules (draft, Phase 2)

The merge is a pure function: `M(e) = merge(M(e−1), logs in manifest e)`. It MUST NOT read the local clock, local indexes, random numbers, or any data outside its inputs. It iterates in sorted order only, and it compares values by their encodings.

### 7.1 Per-row merge

For each row that at least one log changed, in `row_id` order:

1. Group the changes by node, in node ID order. For each node, keep its first before-image and its last after-image.
2. If one node changed the row, take its after-image.
3. If more than one node changed it, and any change is a delete, apply the table's delete rule (Section 7.3).
4. Otherwise merge each column. A node changed a column if its after-image differs from its own before-image (not from the current value). If no node changed it, keep it. If all changing nodes wrote the same value, take it. Otherwise apply the column policy.

### 7.2 Column policies

| Policy | Result | Conflict row |
| --- | --- | --- |
| `lww` | value with the highest stamp | none |
| `lww_flag` | as `lww` | one, with the losing values |
| `delta` | current + Σ(after − before) over writers; INTEGER or DECIMAL only, never REAL | none (a broken check is a constraint conflict) |
| `max`, `min` | largest or smallest value, by encoding order | none |
| `union` | (current ∪ all additions) − all removals | none |
| `text3` | line-level three-way merge, in node ID order | one per overlapping hunk |
| `flag` | keep the current value | one, with all values |

The stamp of a merged column is the highest stamp among its writers.

### 7.3 Delete rules

| Rule | Result | Conflict row |
| --- | --- | --- |
| `delete_wins` (default) | tombstone | the updates |
| `update_wins` | live row with the merged updates | the delete |
| `flag` | tombstone with the updates attached | one |

### 7.4 Constraint pass

After all rows merge, in this order:

1. **Unique keys.** The row whose insert has the lowest stamp keeps the value. Each other row becomes a tombstone, and a conflict row names the winner.
2. **Foreign keys.** A deleted parent with a live child is restored from `M(e−1)`, unless the table selects cascade. A conflict row names both changes.
3. **Check constraints.** The result stays. A conflict row records the break.

### 7.5 Conflicts

```
conflict_id = BLAKE3-derive-key(conflict id context,
                epoch:u64 || len32(table name) || row_id:16
                || column:u16 (0xFFFF for a whole row) || kind:u8)
```

Conflict rows are sorted by (table, row_id, column). The `_conflicts` table is a normal replicated table.

## 8. State hash (draft, Phase 1)

A Prolly tree maps `row_id` (16 bytes) to `row_hash` (32 bytes), over all rows, tombstones included. Node boundaries come from the hash of each key, so the tree shape depends only on the set of rows, not on the order of inserts. The root hash is `H(e)`. Phase 1 fixes the chunking rule and its target node size.

## 9. Differences from the white paper

| Topic | White paper | This specification | Reason |
| --- | --- | --- | --- |
| NaN | not covered | one canonical NaN | NaN bits differ between CPUs |
| Decimal | `DECIMAL(10,2)` | stored normalized | one encoding per number |
| Text | not covered | bytes, no Unicode normalization | normalization depends on the Unicode version |
| `max` / `min` order | "largest" | encoding order | byte-wise and the same on every node |
| HLC overflow | not covered | counter carries into physical time | keeps the clock monotonic |
| HLC restart | not covered | persisted upper bound | the clock must not go backward |
| Stamps in the root hash | row hash is a hash of "row content" | stamps are part of the row | later merges read the stamps |
| Hash function | not named | BLAKE3 with a context per kind | fast, and no confusion between hash kinds |
